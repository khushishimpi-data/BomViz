# API

The live OpenAPI document is generated by FastAPI:

- Swagger UI: <http://localhost:8000/api/v1/docs>
- JSON: <http://localhost:8000/api/v1/openapi.json>

This page records conventions and the contract. Endpoints are marked with the phase that
delivers them; ✅ marks a delivered phase, unmarked phases are planned.

## Conventions

- Versioned under `/api/v1`. Health probes are unversioned.
- JSON request and response bodies. File uploads use `multipart/form-data`.
- `Authorization: Bearer <access_token>` on every endpoint except register, login, refresh,
  logout and health. A 401 caused by the bearer token carries `WWW-Authenticate: Bearer`.
- List endpoints accept `limit` (default 50, max 200) and `offset`, and return
  `{items, total, limit, offset}`.
- Every response carries `X-Request-ID`. A client may send a safe value
  (`[A-Za-z0-9._-]{1,64}`) to correlate requests.
- Errors always use this envelope:

```json
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "BOM contains blocking validation errors.",
    "details": [],
    "request_id": "6f1c…"
  }
}
```

| Code | HTTP | Meaning |
|---|---|---|
| `VALIDATION_ERROR` | 422 | Request body or query failed schema validation (`details[].field`). Also returned by the register password policy (12–128 characters, must not equal the email, compared case-insensitively). |
| `UNAUTHENTICATED` | 401 | No `Authorization: Bearer` header, or `/auth/refresh` called without a refresh cookie |
| `TOKEN_EXPIRED`, `TOKEN_INVALID` | 401 | The access token, or the refresh cookie on `/auth/refresh`, has expired or was rejected. A refresh cookie already revoked by logout is `TOKEN_INVALID`. |
| `TOKEN_REUSED` | 401 | A refresh token that was already rotated (replaced by a successor) was presented; every session of that user is revoked |
| `INVALID_CREDENTIALS` | 401 | Login failed. Wrong password, unknown email and inactive account all return this code |
| `FORBIDDEN` | 403 | Authenticated but the role lacks permission |
| `NOT_FOUND` | 404 | Missing, or in a workspace the caller cannot access |
| `USER_NOT_FOUND` | 404 | Adding a member: no account has that email |
| `EMAIL_TAKEN` | 409 | Register: an account with this email already exists |
| `ALREADY_MEMBER` | 409 | Adding a member: the user already belongs to the workspace |
| `LAST_ADMIN` | 409 | The change would demote or remove the workspace's last `ADMIN` |
| `SLUG_TAKEN` | 409 | Creating a workspace with a supplied slug that is already in use, or with a derived slug when all 5 suffixed attempts collide |
| `PRODUCT_CODE_TAKEN` | 409 | The `product_code` already exists in the workspace |
| `REVISION_CODE_TAKEN` | 409 | The `revision_code` already exists for the product |
| `CONFLICT`, `INVALID_STATE`, `DUPLICATE_UPLOAD`, `VALIDATION_FAILED` | 409 | State conflicts |
| `RATE_LIMITED` | 429 | A rate limit (per client IP, or per user for adding members) was exceeded; `Retry-After` gives the seconds to wait |
| `LOGIN_THROTTLED` | 429 | Too many failed logins for this (email, IP) pair; `Retry-After` gives the seconds to wait |
| `UNSUPPORTED_FILE_TYPE` | 400 | Not `.csv`, `.xlsx` or `.xls` |
| `FILE_TOO_LARGE` | 413 | Over 20 MB |
| `INTERNAL_ERROR` | 500 | Unexpected failure; message is generic, `request_id` identifies the log entry |

## Endpoints

|---|---|---|
| GET | `/health` | `200 {status: "ok", version}` |

### Auth (Phase 1) ✅

| Method | Path | Body | Response |
|---|---|---|---|
| POST | `/auth/register` | `{email, password, full_name}` | `201 User`. Does not sign in. |
| POST | `/auth/login` | `{email, password}` | `200 {access_token, token_type: "bearer", expires_in, user}` + refresh cookie |
| POST | `/auth/refresh` | refresh cookie | `200 {access_token, token_type, expires_in}` (rotates cookie) |
| POST | `/auth/logout` | refresh cookie | `204`. Revokes the cookie's session and always clears the cookie. Idempotent; no bearer token needed. |
| GET | `/auth/me` | none | `200 User + memberships: [{workspace_id, workspace_name, workspace_slug, role}]` |

`User` is `{id, email, full_name, is_active, created_at}`. It never contains the password hash.
`expires_in` is the access token lifetime in seconds.

Request rules:

- **Register.** `email` must be a valid address and is lower-cased. `password` must be 12–128
  characters and must not equal the email (compared case-insensitively). `full_name` must be
  1–200 characters after stripping. Unknown fields are rejected.
- **Login.** A wrong password, an unknown email and an inactive account all return the same
  `401 INVALID_CREDENTIALS` (`"Invalid email or password."`). Throttling treats unknown emails
  exactly like known ones, so neither the 401 nor the 429 reveals whether an account exists.
  Concurrent attempts on one (email, IP) pair are serialized with a PostgreSQL advisory lock,
  so a burst of parallel requests gets no more password checks than sequential ones.
- **Refresh.** Rotation keeps the session's original expiry: a session lives at most
  `REFRESH_TOKEN_TTL_DAYS` from login, however often it is refreshed. Outcomes by cookie:
  - Unknown → `401 TOKEN_INVALID`.
  - Already rotated (it has a successor) → reuse: every refresh token of the user is revoked,
    `AUTH_REFRESH_REUSED` is audited, `401 TOKEN_REUSED`.
  - Revoked by logout (no successor) → `401 TOKEN_INVALID`; nothing else is revoked.
  - Expired → `401 TOKEN_EXPIRED`.

  Every rejected cookie is cleared in the error response.
- **Logout.** The presented token's row is locked before its family is revoked, so logout
  serializes with a concurrent refresh of the same session and also revokes the successor that
  refresh created.

**Refresh cookie.** `bomviz_refresh`, `HttpOnly`, `SameSite=Strict`, `Path=/api/v1/auth`,
`Max-Age` = the seconds left in the session (`REFRESH_TOKEN_TTL_DAYS` at login, then shrinking,
because rotation keeps the original expiry). `Secure` comes from `REFRESH_COOKIE_SECURE`, which must
be `true` in production. The raw token is never returned in a response body, and the server
stores only its SHA-256 hash.

**Rate limits.** Each limit is a Redis fixed window. Exceeding one returns
`429 RATE_LIMITED` with `Retry-After`.

| Endpoint | Limit | Identity |
|---|---|---|
| `POST /auth/register` | 5 per hour | client IP |
| `POST /auth/login` | 30 per 15 minutes | client IP |
| `POST /auth/refresh` | 60 per 15 minutes | client IP |
| `POST /workspaces/{id}/members` | 30 per hour | acting user (bucket `member_add`) |

If Redis is unavailable, the limiter fails open and logs `rate_limiter_unavailable`.
`RATE_LIMIT_ENABLED=false` turns the limits off.

**Client IP.** The IP used for rate limits and the login throttle is resolved as follows:

- By default it is the direct peer address, and `X-Forwarded-For` is ignored.
- When the direct peer is listed in `TRUSTED_PROXY_IPS` (comma-separated IPs or CIDRs, default
  empty), it is the right-most `X-Forwarded-For` entry that is not itself a trusted proxy.
  Entries to its left are ignored, because the client can forge them. If no such entry
  exists, the peer is used.
- An IPv4-mapped IPv6 address is treated as its IPv4 address. Any other IPv6 address is
  identified by its /64 network, so rotating addresses within one /64 does not escape a limit.
- An invalid `TRUSTED_PROXY_IPS` entry stops the backend at startup.

Docker Compose trusts exactly the frontend container (`172.30.0.10`), whose Vite dev proxy
appends `X-Forwarded-For`. Requests sent straight to port 8000 cannot spoof the header.

> **Deployment.** Behind any other reverse proxy or load balancer, set `TRUSTED_PROXY_IPS` to
> its address(es). Otherwise every client appears to come from the proxy, and they all share
> one identity: one set of IP rate limits for everyone, and one login throttle per email.

**Progressive login throttle.** Failed logins are also counted per (email, IP) pair, separately
from the per-IP limit:

| Failure count | Block after that failure |
|---|---|
| 1–3 | none |
| 4 | 30 s |
| 5 | 60 s |
| 6 | 120 s |
| … | doubles each time, capped at 900 s (15 min) |

While a pair is blocked, login returns `429 LOGIN_THROTTLED`
(`"Too many sign-in attempts. Please wait and try again."`) with `Retry-After` set to the
remaining seconds. The password is not checked while blocked.

- A successful login clears the pair's counter.
- A counter with no failure in the last 24 hours starts again from zero.
- The pair is stored only as a SHA-256 hash. The raw email and IP are never stored.
- Settings: `LOGIN_FREE_ATTEMPTS` (4), `LOGIN_BASE_DELAY_SECONDS` (30),
  `LOGIN_MAX_DELAY_SECONDS` (900), `LOGIN_THROTTLE_RESET_HOURS` (24).

### Workspaces, members and products (Phase 1) ✅

Every endpoint requires a bearer token. Inside a workspace, the caller's role in that workspace
decides access (see [Roles and permissions](#roles-and-permissions)).

- A workspace the caller does not belong to, and anything inside it, returns `404 NOT_FOUND`.
- A member whose role lacks the permission gets `403 FORBIDDEN`.

| Method | Path | Permission | Body | Response |
|---|---|---|---|---|
| POST | `/workspaces` | authenticated | `{name, slug?}` | `201 Workspace`. The caller becomes owner and `ADMIN`. `409 SLUG_TAKEN` |
| GET | `/workspaces` | authenticated | none | `200` page of `Workspace` the caller belongs to |
| GET | `/workspaces/{id}` | `workspace:read` | none | `200 Workspace` |
| GET | `/workspaces/{id}/members` | `workspace:read` | none | `200` page of `Member` |
| POST | `/workspaces/{id}/members` | `workspace:manage_members` | `{email, role}` | `201 Member`. `404 USER_NOT_FOUND`, `409 ALREADY_MEMBER`, `429 RATE_LIMITED` |
| PATCH | `/workspaces/{id}/members/{member_id}` | `workspace:manage_members` | `{role}` | `200 Member`. `409 LAST_ADMIN` |
| DELETE | `/workspaces/{id}/members/{member_id}` | `workspace:manage_members` | none | `204`. `409 LAST_ADMIN` |
| POST | `/workspaces/{id}/products` | `product:write` | `{product_code, name, description?, status?}` | `201 Product`. `409 PRODUCT_CODE_TAKEN` |
| GET | `/workspaces/{id}/products` | `product:read` | none | `200` page of `Product`, ordered by `product_code`; filters `q`, `status` |
| GET | `/products/{id}` | `product:read` | none | `200 Product + revisions` (newest first) |
| POST | `/products/{id}/revisions` | `product:write` | `{revision_code, description?, status?}` | `201 Revision`. `409 REVISION_CODE_TAKEN` |

- `Workspace` is `{id, name, slug, owner_id, role, created_at}`, where `role` is the caller's
  role.
- `Member` is `{id, user_id, email, full_name, role, created_at}`. `id` is the membership id
  used as `member_id`. Members are listed by `full_name`, then `email`. Workspaces are listed
  by `name`.
- `Product` is `{id, workspace_id, product_code, name, description, status, created_by_id,
  created_at, updated_at}`. `description` and `created_by_id` may be `null`.
- `Revision` is `{id, product_id, revision_code, description, status, created_by_id,
  created_at}`. `description` and `created_by_id` may be `null`. `GET /products/{id}` returns
  the `Product` fields plus `revisions`, newest first.
- **Workspace body.** `name` is 1–100 characters. `slug` is optional: 3–48 characters matching
  `^[a-z0-9]+(?:-[a-z0-9]+)*$`. A supplied slug that is in use returns `409 SLUG_TAKEN`.
  When the slug is omitted it is derived from the name (ASCII, lowercase, hyphens, at most 40
  characters):
  - On collision, `-` plus 4 random hex characters is appended, up to 5 attempts. If all 5
    collide, the response is `409 SLUG_TAKEN`, and the client should supply a slug.
  - A derived slug shorter than 3 characters always gets the suffix.
- **Add member.** Limited to 30 attempts per hour per acting user (bucket `member_add`).
  Exceeding it returns `429 RATE_LIMITED` with `Retry-After`. The limit is counted only after
  the membership and permission check, so non-admins and non-members never use it up.
- **Product body.** `product_code` is 1–64 characters, `name` 1–200, `description` up to 2000
  (all stripped). `status` is `DRAFT | ACTIVE | OBSOLETE` (default `DRAFT`).
- **Revision body.** `revision_code` is 1–32 characters, `description` up to 2000 (both
  stripped). `status` is `DRAFT | RELEASED | OBSOLETE` (default `DRAFT`).
- An empty or whitespace-only `description` is stored as `null`, on products and revisions.
- **Product search `q`.** A case-insensitive substring match on `product_code` or `name`.
  - At most 200 characters; a longer value returns `422 VALIDATION_ERROR`.
  - Leading and trailing whitespace is stripped, and a blank `q` applies no filter.
  - `%`, `_` and `\` match literally; they are not wildcards.
- Products and revisions cannot be edited or deleted in Phase 1, and workspaces cannot be
  deleted.
- Members are added by the email of an existing account. There are no invitations.
- **Member removal** deletes only the membership. The user account and every audit row they
  authored are kept. The last `ADMIN` of a workspace can never be demoted or removed
  (`409 LAST_ADMIN`).

### Roles and permissions

Roles are per workspace (`workspace_members.role`), so a user may hold a different role in each
workspace. The policy lives in `backend/app/core/permissions.py` and denies by default.

| Role | `workspace:read` | `workspace:manage_members` | `product:read` | `product:write` |
|---|---|---|---|---|
| `ADMIN` | yes | yes | yes | yes |
| `ENGINEER` | yes | no | yes | yes |
| `PROCUREMENT` | yes | no | yes | no |
| `PRODUCTION` | yes | no | yes | no |
| `VIEWER` | yes | no | yes | no |

### Audit events (Phase 1)

Audit rows are written in the same transaction as the change and carry the request's
`request_id`. Failed logins, blocked attempts and refresh-token reuse are committed even though
the request fails. Phase 1 has no endpoint for reading audit logs.

| Action | Written when |
|---|---|
| `AUTH_REGISTERED` | An account is created |
| `AUTH_LOGIN_SUCCEEDED` | Login succeeds |
| `AUTH_LOGIN_FAILED` | Login fails; metadata `{reason: "bad_password" \| "inactive" \| "unknown_user", failure_count}` |
| `AUTH_LOGIN_THROTTLED` | A failure starts a block; metadata `{failure_count, delay_seconds}` |
| `AUTH_LOGIN_BLOCKED_ATTEMPT` | A login is rejected while blocked; metadata `{retry_after_seconds}` |
| `AUTH_REFRESH_REUSED` | A rotated refresh token is presented again |
| `AUTH_LOGGED_OUT` | Logout revokes a session |
| `WORKSPACE_CREATED` | A workspace is created |
| `MEMBER_ADDED` | A member is added; metadata `{target_user_id, role}` |
| `MEMBER_ROLE_CHANGED` | A member's role changes; metadata `{target_user_id, from, to}` |
| `MEMBER_REMOVED` | A membership is deleted; metadata `{target_user_id, previous_role}` |
| `PRODUCT_CREATED` | A product is created |
| `PRODUCT_REVISION_CREATED` | A revision is created |

Audit metadata never contains emails, IP addresses, passwords, tokens or throttle key hashes.
`AuditService.record` rejects keys that look like those as a programming error. For login
events, the actor is the user when the email belongs to an account, and `NULL` otherwise.
